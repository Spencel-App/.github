# Contributing to Spencel

Thanks for taking the time to help make Spencel better. Whether it's a bug report, a
feature idea, a doc fix, or a pull request, it's genuinely appreciated.

These guidelines apply across the Spencel organization. Individual repositories may add
their own setup steps in their README — read those first for the project you're working
in.

## Ways to contribute

- **Report a bug** — open an issue using the Bug report template.
- **Suggest a feature** — open an issue using the Feature request template. The more it's
  framed as the problem you're trying to solve, the better.
- **Improve the docs** — typos, unclear steps, and missing context are all fair game.
- **Send a pull request** — fixes and improvements are welcome. For anything large, open
  an issue first so we can agree on the approach before you spend time on it.

## Before you start

- Search existing issues and pull requests to avoid duplicates.
- For non-trivial changes, open an issue to discuss it first.
- Keep changes focused. One concern per pull request is much easier to review.

## Development workflow

1. **Fork and branch.** Create a branch off `main` with a short, descriptive name
   (e.g. `fix/subscription-dedupe` or `feat/csv-import`).
2. **Set up the project.** Follow the setup instructions in the relevant repo's README.
3. **Make your change.** Match the existing code style and conventions in that repo.
4. **Test it.** Run the project's test and type-check commands, and verify your change by
   hand where it makes sense. Don't rely on mock data to "pass" — make sure the real path
   works.
5. **Write a clear commit message.** Explain what changed and why.
6. **Open a pull request.** Fill out the pull request template and link any related issue.

## Pull request expectations

- Describe what the change does and why it's needed.
- Note anything reviewers should pay attention to, and anything you couldn't verify.
- Keep the diff as small as the change allows.
- Be responsive to review feedback — we try to be the same in return.

## Code of conduct

Participation in this project is governed by our
[Code of Conduct](./CODE_OF_CONDUCT.md). By taking part, you agree to uphold it.

## Security issues

Please **do not** open public issues for security vulnerabilities. See
[SECURITY.md](./SECURITY.md) for how to report them responsibly.

## Questions

If you're not sure where something belongs or how to approach it, open an issue and ask.
We'd rather talk early than have you guess.
